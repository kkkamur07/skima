# Adopt from the Web UI, but adopt through the CLI

ADR-0009 put the line in a sensible place: the **Web UI** is a local-only lens onto a directory, and the **CLI** is where machine actions live. `web/README.md` said so outright — "Adoption, sync, and install stay in the CLI. There is no adopt or update button here." For sync and **Check** that holds up fine; they are things you fire off and read the result of, and nothing about them wants a page.

**Adoption** does not fit that shape. Deciding to adopt a skill means reading it — the frontmatter, the actual instructions, what else the directory ships — and then deciding where in the **Library** it belongs. That is browsing, and browsing a **Source** tree in a terminal is miserable: `ls sources/*/skills/`, open a `SKILL.md`, back out, guess at the next path, repeat across eight repositories. The information you need in order to say yes lived on the surface ADR-0009 built for exactly this kind of looking, and the action lived on the other one.

We considered leaving it alone and having the **Web UI** print a copy-pasteable `skima adopt` line. It is honest, and it is also a worse version of the same thing: the user still has to leave the page, and the button we did not build would have been trivially safer than a command line assembled by hand from a page and pasted into a shell.

We considered implementing **Adoption** in the web server instead. That was the real temptation and the thing to reject. `skima adopt` carries rules that are the whole point of the word deliberate: it never guesses a **Bucket** (the caller names it), it takes the **Id** from the upstream directory per ADR-0006, it infers **Kind** from the tree, and it refuses outright when that **Id** is already anywhere in the **Library**. It also stages the whole copy into a hidden temporary directory and renames it into place, so an interrupted adopt leaves rubbish to delete rather than a half-populated **Capability** that **Install** would cheerfully symlink into every **Agent**. A second implementation would have to reproduce every one of those, and would drift from the first the day either changed — with the failure showing up as two surfaces disagreeing about what is allowed.

We chose: the surface moves and the implementation does not. The **Web UI** gains an **Explore** page that browses the tracked **Sources**, lists the **Capabilities** inside them, and puts an "Add to Library" action on each. `POST /api/adopt` and `POST /api/install` shell out to `cli/skima adopt` and `cli/skima install`. There is exactly one implementation of **Adoption**, and the terminal and the browser both go through it.

The new command is `skima adopt <source> [upstream-path] --bucket <bucket> [--kind <kind>] [--id <id>]`, and nothing in it exists for the browser's benefit. It is the command you would want anyway; the page is a way of filling in its arguments after reading the thing you are about to adopt.

The server does validate the request first — **Bucket** name, **Kind**, **Id**, and that the upstream path really is a directory inside that **Source**. That validation is for the error message, not for safety. It exists so the browser gets "'deprecated' is not a usable Bucket name" instead of a shell transcript. The **CLI** re-checks all of it, because the **CLI** is also what a terminal invocation goes through, and a check that only runs on one of two paths protects neither.

ADR-0009's boundary is untouched by this. Adopt and install are state-changing POSTs behind the same loopback bind, `Origin` and `Host` validation, and now a write lock, so a double click cannot interleave an adopt with an install reading the **Library** it is writing into.

**Explore** stops short of updating. It shows, per **Capability**, whether it is already a **Library copy** — matched on **Provenance** first, falling back to **Id** — and whether that copy's recorded **Revision** trails the **Source**'s current pin. It offers no button for it. Bringing a **Library copy** forward is a **Change review** decision with a diff behind it, and there is no diff yet; flagging it as worth a look is as far as **Explore** is entitled to go.

Consequence: every future adopt-like action — update an adopted copy, deprecate one, remove one — has to land in the **CLI** first and be reached from the **Web UI** by invoking it. The moment a mutation is written directly into the server, the two surfaces begin to diverge in what they enforce, and the **CLI** quietly stops being the thing that is true about the **Library**.
