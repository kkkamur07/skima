# Capabilities in a Source tree are recognised by shape

ADR-0004 settled discovery inside the **Library**: the **Capability record** marks a directory as a **Capability**, so nothing has to guess from file globs — which is what keeps a nested translation like `docs/de/SKILL.md` from being counted as a second **Capability**. That works because Skima wrote the record.

A **Source** tree gets none of that. It is upstream's layout, committed verbatim at a pinned **Revision**, and it must stay that way: writing a record into `sources/` would put a local edit into the baseline that **Change review** diffs against, which is the same corruption the `.gitignore` negations were added to prevent. So the **Explore** page has to answer "what is adoptable in here" with no help from Skima's own metadata.

We considered a hand-maintained manifest per **Source** listing the adoptable paths. It is stale on the first sync — upstream adds a skill and the manifest does not know — and it is precisely the central index ADR-0004 rejected, only now there is one of them per **Source**.

We chose to recognise **Capabilities** by marker file: a directory holding `SKILL.md` is **Kind** `skill`, one holding `.claude-plugin/plugin.json` is `plugin`, and a `hooks/` directory holding `hooks.json` is `hook`. These are not conventions Skima invented. They are the files the consuming **Agents** themselves key off, which makes them the closest thing to a declaration of intent that upstream actually ships.

The tie-break the record used to provide comes back as a traversal rule: skills are outermost-wins. Once a directory is claimed by its `SKILL.md`, its whole subtree belongs to it and is not searched further. That is what stops `sources/socratic-method-skill/docs/de/SKILL.md` — a translation of the skill above it — from being offered as a **Capability** of its own. The repository root is still considered separately when it carries a plugin manifest, because a repo can be one plugin and still ship the individual skills inside it as separately adoptable things.

Agent definitions and slash commands are deliberately not adoptable on their own. An agent is a single `agents/<name>.md` and a command a single `commands/<name>.toml`, and a **Capability** is a directory — that is what the `library/<bucket>/<id>/` layout, the **Capability record** living inside it, and symlink **Install** all assume. Making a loose file adoptable would mean either inventing a wrapper directory that has no upstream counterpart, and so no reviewable **Provenance** path, or teaching **Install** a second materialisation shape. Both cost more than the problem is worth, so **Explore** counts and lists agents and commands as part of what a plugin brings rather than offering them separately.

What discovery produces is a proposal, not a verdict. The **Id** and **Kind** it shows are what `skima adopt` would derive anyway, and both can be overridden at adoption with `--id` and `--kind`. The **CLI** does no scanning of its own — it is given an explicit upstream path — so the only rule stated in both places is the plugin-versus-skill **Kind** inference, duplicated on purpose so the **CLI** still works with no server running.

Consequence: a **Source** that ships something in a shape Skima does not recognise is invisible on **Explore**. That is accepted rather than papered over with looser matching, because looser matching is how `docs/de/SKILL.md` gets offered again. The fallback is `skima adopt <source> <path>` by hand, which never consulted discovery in the first place, and the fix is to add a marker to the list when a genuinely new shape turns up.
